## Why

一次真实运行（在 Mac 上关闭一个代理应用的 TUN 开关，共 116.8 秒、7 步）暴露了四个问题：

- **目标只是一句话，代码判断不了完成没有。** 最后只能请写手去读“TUN模式已关闭”这段文案，多花了一轮写手调用。
- **分类器在 91 个候选里自由选。** 同名的行标题和真开关之间只差 0.04；一个被描述成“加载指示器”的图标也进了候选。
- **高于门槛就执行，不看第一名领先多少。** 0.41 对 0.37 也照样执行，白点了一次。
- **点击没效果时，下一步还在同一屏上重新判断。** 要连续三次没变化才算卡住，结果 driver 又花了 5 步、约 55 秒去探索。

分类器适合当局部执行器，不适合做规划；规划需要另一层，按需调用、滚动生成。现在要加这一层，主循环是阻碍。分类器、写手、driver 的交接写在 `runner.run`、`hand_off` 和 `wants_driver` 的条件分支里，结局用 `outcome` 和 `route` 两个字符串表达，再加任何一层都要改这几处分支。所以这次参照 UFO2 的代码架构（agent 工厂、agent、状态、按阶段的策略、中间件），先把执行过程重构成可以组合的结构，再在上面加规划。

## What Changes

**阶段一：重构执行过程，外部行为不变**

- 运行由一个主循环驱动：循环里每轮由工厂按状态取一个 agent 执行，执行结果决定下一个状态。四个 agent 是宿主、分类器、写手、接管，对应今天的 `host.prepare`、`run_step`、`hand_off`、`take_over`。
- 状态用一个枚举加一张状态转移表表达，取代分散的条件分支。`run.json` 里的 `outcome` 与写手的 `route` 取值不变，改为从状态推出来。
- 分类器的一步拆成感知、决策、执行、记忆四个阶段，每个阶段是一个可替换的策略。截屏到执行的现有逻辑原样搬进去。
- 计时、写 `step-NNN-*` 文件、向子会话控制端上报动作、写运行日志，改由包在每一步外面的中间件完成。
- `runner.py` 对外只保留 `RunConfig` 与 `run()`，`cli.py`、`helper/service.py`、`waa/agent.py` 不用改。**BREAKING（仅限测试）**：测试改为引用新模块里的函数。
- 判定标准：同一份回放数据在重构前后得到相同的历史、结局、`run.json` 键集合和每一步的文件。

**阶段二：在分类器之上加规划层（Windows 先行）**

- **按需规划。** 首步分类器的分差足够大时，直接执行，不规划。分差小，或分类器停下时，用写手模型规划一次，输出一条目标状态断言和 2 到 3 个子目标；每个子目标带动作空间和验收条件。最多重规划 2 次，一次运行累计最多 5 个子目标。次数用完就交给现有的写手和接管路径。
- **用状态断言判定完成。** 子目标和整个目标是否达成，由代码读控件状态判定（已勾选、当前值、已展开），结果为真、假或未知。未知时退回由写手读屏判断。Windows 的无障碍树已经报告这些状态；macOS 读不到，断言总是未知。
- **缩小候选集，并能逐级放宽。** 分类器只在子目标的动作空间里选，编号与全量候选一致。空间里没有候选，或分差仍然太小，就逐级放宽：先只按标签，再回到全部候选。
- **先合并同一目标的候选，再算分差。** 框重叠或同一行同名的候选概率相加之后，再看第一名和第二名差多少。分差太小时不执行，而是放宽或缩小候选后再问。
- **一次没效果就换按法。** 屏幕指纹加入控件状态，使开关翻转算作有变化。指纹没变、断言也没成立时，下一次换一种按法（无障碍按下和坐标点击互换），而不是在同一屏上再判断一遍。
- 新增配置：`planner`（默认开）、`plan_skip_margin`（0.3）、`decide_margin`（0.15）、`max_replans`（2）、`max_subgoals`（5）。`run.json` 增加计划、断言结果、放宽次数、重规划次数与规划耗时；规划一次写一份 `step-NNN-plan.json`。

不在本次范围内：

- 把成功的计划存成带断言的宏并回放。
- macOS 读开关状态。
- 分类器一次给多步。
- UFO2 的异步执行、每个状态一个单例类、策略依赖校验、多 agent 并发的黑板。
- 浏览器路径（`browser/`）自己的循环。

## Capabilities

### New Capabilities

- `run-lifecycle`：一次运行由谁在什么时候接手。包括宿主、分类器、写手、接管与规划之间的交接条件，每种结局在 `run.json` 里的写法，每一步在运行目录里留下的文件，以及重构前后这些外部可见结果保持一致的要求。
- `goal-planner`：规划层的行为。包括何时跳过规划、计划的结构与上限、滚动生成与重规划的次数、规划失败或用完次数时的去向，以及计划在运行记录里的写法。
- `subgoal-verification`：子目标如何约束分类器并判定完成。包括动作空间的过滤与逐级放宽、合并同一目标的候选后的分差规则、控件状态断言的真/假/未知三种结果、含控件状态的屏幕指纹，以及一次没效果后的换按法。

### Modified Capabilities

（无。现有规格覆盖的是感知、截图和 WAA，本次不改它们的要求。）

## Impact

- **代码**
  - 新增 `yuanji_computer_use/agents/` 包，含工厂、状态、会话与每步上下文、策略、中间件、四个 agent 和规划器。
  - `runner.py` 只保留主循环和写 `run.json`。
  - `driver.py` 现在在函数里懒导入 `runner` 来拿判定屏幕变化的函数，改为直接从策略模块导入。
  - `decide.py`：只交出一部分候选，并计算合并同一目标后的分差。
  - `models.py`：屏幕指纹加入控件状态。
  - `actions.py`：`click_item` 可以指定换一种按法。
  - `writer.py`：新增生成计划的调用。
  - `config.py`：新增配置项。
- **测试**：16 个直接引用 `runner` 内部函数的测试文件改为引用新模块，断言内容不改。新增状态转移、工厂懒加载、中间件、规划和各个机制的离线测试。`tests/conftest.py` 的机器守护：预计没有新增会触及机器的调用；若实现中出现，同一批改动里加入。
- **导入边界**：接管模块（会导入 Agents SDK）仍然只在接管真正发生时才导入。
- **模型调用**：需要规划时多一次写手模型调用（预计 3 到 5 秒）。单步任务因为跳过规划，调用次数不变。
- **文档**：`docs/how-a-step-works.md` 增加“agent 与状态”和“规划”两节；`docs/writer-endpoints.md` 加新配置项；`CONTRIBUTING.md` 更新模块布局。
- **验证**：在 Windows 上用一个开关类目标做对照（关掉规划和默认配置各跑一次），每条命令都需要维护者事先批准。
